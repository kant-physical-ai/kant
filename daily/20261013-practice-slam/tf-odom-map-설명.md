# map / odom / base_footprint — 보정은 무엇을 움직이나

## 0. 결론

- SLAM 보정은 **`map→odom` 변환 하나만** 바꾼다.
- `odom→base_footprint`(바퀴로 센 값)는 절대 건드리지 않는다.
- 로봇의 map 위치(`map→base_footprint`)는 두 변환을 **합성**해서 나온다. 단순 덧셈이 아니다.

## 1. 프레임 3개와 누가 발행하나

| 변환 | 발행 주체 (이 실습) | 성질 |
|---|---|---|
| `odom → base_footprint` | Gazebo `DiffDrive` 플러그인 (바퀴 관절 회전으로 계산) | 연속적, 점프 없음, 오차가 계속 쌓임 |
| `map → odom` | Cartographer | 오차를 상쇄하는 보정값, **점프할 수 있음** |
| `map → base_footprint` | 아무도 직접 발행 안 함 (TF가 위 둘을 합성) | 보정된 로봇 위치 |

이 실습 설정(`config/turtlebot3_lds_2d.lua`)이 그렇게 되어 있다.

- `provide_odom_frame = false`: odom 프레임은 Cartographer가 만들지 않고 Gazebo 것을 쓴다.
- `published_frame = "odom"`: Cartographer는 `map → odom`만 발행한다.
- `use_odometry = true`: `/odom`을 입력으로 받아 scan 매칭에 같이 쓴다.

**왜 굳이 두 단계로 나누나?** (ROS 표준 REP-105)

- TF 트리에서 한 프레임의 부모는 하나뿐이다. `base_footprint`의 부모를 `odom`으로 두고, 보정은 그 위(`map→odom`)에 얹는다.
- 바퀴 제어나 장애물 회피처럼 **짧은 구간을 부드럽게** 봐야 하는 일은 `odom` 기준으로 한다. 점프가 없기 때문이다.
- 전역 경로처럼 **멀리 정확해야** 하는 일은 `map` 기준으로 한다. 가끔 점프하지만 오차가 없다.

## 2. 합성 공식

변환 하나는 "회전 + 이동"이다. 두 변환을 이으면:

```
map->base 위치 = R(map->odom) * (odom->base 위치) + t(map->odom)
map->base 방향 = yaw(map->odom) + yaw(odom->base)
```

- `R(...)`: 회전, `t(...)`: 이동
- **`map→odom`에 회전이 0일 때만** 위치를 그냥 더하면 된다: `map->base = t(map->odom) + odom->base`
- 실제 바퀴 오차는 대부분 **방향(yaw) 오차**라서 보통 회전이 들어간다. → 예시 3

## 3. 예시 1: 1m 직진했는데 odom은 1.1m

바퀴가 미끄러져서 헛돈 만큼 더 셌다. scan 매칭 결과 실제 이동은 1.0m.

| 변환 | 값 | 설명 |
|---|---|---|
| `odom → base` | +1.1 | 바퀴가 센 값. 그대로 둔다 |
| `map → odom` | **−0.1** | Cartographer가 거는 보정값 |
| `map → base` | −0.1 + 1.1 = **+1.0** | 보정된 위치 |

map 위에 그리면 (`O` = odom 원점, `M` = map 원점, `R` = 로봇):

```
  -0.1 0.0                                     1.0   <- map x (m)
    O   M                                       R
    |   |                                       |
    |<->|  map->odom  = -0.1
        |<--------- map->base  = 1.0 ---------->|
    |<----------- odom->base = 1.1 ------------>|
```

- 로봇은 **한 곳**에 있다. map 기준으로 1.0m, odom 기준으로 1.1m일 뿐이다.
- 보정은 로봇을 옮기는 게 아니라 **odom 원점을 0.1m 뒤로 옮기는 것**이다.

## 4. RViz에서 보이는 것

TF 표시에서 `odom` 축은 **odom 프레임의 원점**(바퀴 적산이 시작된 자리)을 그린 것이다. "odom이 생각하는 로봇 위치"가 아니다.

**Fixed Frame = `map` 일 때**

- `map` 축: 고정
- `odom` 축: map 원점 근처에 있다가 보정될 때마다 **툭툭 움직인다** (예시 1이면 −0.1m 자리)
- 로봇 모델: 벽, scan과 맞는 자리. 큰 보정(loop closure)이 걸리면 로봇도 같이 튄다

**Fixed Frame = `odom` 일 때**

- 로봇 모델: 점프 없이 부드럽게 움직인다
- 지도와 `map` 축: 보정될 때마다 통째로 움직인다

두 화면 모두 정상이다. 무엇을 고정해서 보느냐의 차이다.

## 5. 예시 2: 회전 오차가 없는 2D

teleop으로 몰고 다녔더니, 바퀴는 (5, 5)에 왔다고 세고 scan은 (4, 4)라고 한다. 방향 오차는 없다고 가정한다.

| 변환 | 값 |
|---|---|
| `odom → base` | (5, 5) |
| `map → odom` | (−1, −1), 회전 0 |
| `map → base` | (−1, −1) + (5, 5) = (4, 4) |

```
  5     |                   x        M = map 원점 (0, 0)
  4     |               R            O = odom 원점, map 기준 (-1, -1)
  3     |                            R = 로봇, map 기준 (4, 4)
  2     |                            x = odom 값 (5, 5)를 map에 그냥 찍은 자리 (틀린 위치)
  1     |
  0 +---M---+---+---+---+---+
 -1 O   |
    -1  0   1   2   3   4   5
```

- `O`에서 `R`까지가 `odom→base` = (5, 5)
- `M`에서 `O`까지가 `map→odom` = (−1, −1)
- `R`과 `x` 사이가 1.41m 벌어진 것은 **odom 값을 map 좌표로 착각하면** 생기는 오차다. 실제로 그 자리에 무언가 있는 건 아니다.

> Nav2처럼 map 기준으로 주행하면 로봇은 map에서 (5, 5)가 될 때까지 더 간다. "명령은 (5, 5)인데 (4, 4)에 섰다"는 일은 **odom만 보고 주행할 때** 생긴다.

## 6. 예시 3: 회전 오차가 있을 때 (현실적인 경우)

경로는 동쪽으로 4m, 좌회전 90°, 북쪽으로 4m. 회전할 때 바퀴가 미끄러져 odom은 **100°** 돌았다고 셌다.

| | x | y | yaw |
|---|---|---|---|
| 실제 위치 (`map → base`) | 4.000 | 4.000 | 90° |
| 바퀴가 센 값 (`odom → base`) | 3.305 | 3.939 | 100° |
| 보정값 (`map → odom`) | **0.061** | **0.695** | **−10°** |

**단순 뺄셈은 틀린다.** `실제 − odom` = (0.695, 0.061)인데, 진짜 `map→odom` 이동량은 (0.061, 0.695)이고 −10° 회전까지 붙는다. 회전이 있으면 x와 y가 섞이기 때문이다.

**뺄셈 방식으로 보정하면 어떻게 되나?** 그 자리에서 북쪽으로 1m 더 가 본다.

| 방식 | 계산 결과 (x, y) | 실제 (4.0, 5.0)와 차이 |
|---|---|---|
| 합성 (`R * odom + t`) | (4.000, 5.000) | 0 |
| 뺄셈 보정을 계속 더하기 | (3.826, 4.985) | 0.17m |

방향 오차 10°는 이동할수록 위치 오차로 바뀐다. 그래서 `map→odom`에는 회전이 반드시 들어가야 한다. 바퀴 오도메트리의 오차도 대부분 이렇게 방향에서 시작한다.

## 7. 오차는 누가 들고 있고 어떻게 커지나

- **오차 원본은 `odom→base`에 있다.** 바퀴 적산은 스스로 고칠 방법이 없어서 오차가 계속 쌓이고, 지워지지 않는다.
- **`map→odom`은 그 오차를 상쇄하는 값이다.** 오차가 커지면 같이 커진다. 주행 거리가 아니라 **쌓인 오차**에 비례한다.
- **odom 좌표값 자체 = 실제 이동 + 오차.** 방 안을 돌아다니면 odom 좌표도 방 크기 정도에 오차가 조금 더해진 값이다. 오래 돌렸다고 수백 m가 되지 않는다. 다만 방향 오차 때문에 odom 기준 궤적은 점점 휘어져 보인다.
- **Cartographer도 완벽하지 않다.** 평소에는 가까운 scan끼리 맞추는 local SLAM이라 천천히 조금씩 틀어진다. 같은 장소에 돌아왔을 때 loop closure가 걸리면 전체를 다시 최적화하고, 이때 `map→odom`이 한 번에 크게 튄다.

## 8. 자주 하는 오해

| 오해 | 실제 |
|---|---|
| odom은 명령(`cmd_vel`, 목표)대로 됐다고 믿는 값이다 | 바퀴가 실제로 돈 양을 센 값이다. 미끄러지면 헛돈 만큼 더 센다 |
| 보정되면 odom 값이 (5, 5)에서 (4, 4)로 고쳐진다 | odom 값은 그대로이고 `map→odom`이 바뀐다 |
| RViz의 odom 축은 odom이 생각하는 로봇 위치다 | odom 프레임의 원점이다. 보통 출발점 근처에 있다 |
| odom은 점프 금지라서 odom 축도 안 움직인다 | 점프 금지는 `odom→base`. map에서 본 odom 축은 보정마다 움직인다 |
| `map→odom` = 실제 위치 − odom 위치 | 회전이 0일 때만 맞다. 일반적으로는 합성의 역연산이다 |

## 9. 실습에서 직접 확인하기

```bash
source /opt/ros/lyrical/setup.bash
export ROS_DOMAIN_ID=9

ros2 run tf2_ros tf2_echo odom base_footprint   # 바퀴 적산: 부드럽게 변함
ros2 run tf2_ros tf2_echo map odom              # 보정값: 가끔 툭 바뀜
ros2 run tf2_ros tf2_echo map base_footprint    # 합성 결과
```

- teleop으로 제자리 회전을 여러 번 하면 `map → odom`의 yaw가 조금씩 바뀌는 게 보인다. 회전할 때 바퀴 미끄러짐이 가장 크다.
- Gazebo만 재시작하면 odom 적산이 0으로 돌아간다. Cartographer를 같이 재시작하지 않으면 예전 지도에 새 odom이 붙어서 map 프레임이 엉뚱한 곳에 뜬다. **둘은 같이 재시작한다.**
