# ROS 2 내비게이션 시스템 전체 아키텍처
```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                             [ 하드웨어 센서 레이어 ]                          │
│   바퀴 엔코더 (Encoder)         IMU 센서                   2D 라이다 (LiDAR)     │
└─────────┬────────────────────────┬─────────────────────────────┬────────────┘
          │ (RAW 모터 값)          │ (RAW 가속도/자이로)         │ (RAW 거리값)
          ▼                        ▼                             ▼
┌──────────────────┐     ┌──────────────────┐          ┌──────────────────┐
│ 바퀴 드라이버 노드 │     │  IMU 드라이버 노드 │          │ 라이다 드라이버 노드│
└─────────┬────────┘     └─────────┬────────┘          └─────────┬────────┘
          │                        │                             │
          │ /wheel_odom (토픽)     │ /imu/data (토픽)            │
          └───────────┬────────────┘                             │ /scan (토픽)
                      │                                          │
                      ▼                                          │
┌──────────────────────────────────────────┐                     │
│ 1단계: EKF 노드 (robot_localization)     │                     │
│  - 바퀴/IMU 데이터를 센서 퓨전 (노이즈 제거) │                     │
└─────────────────────┬────────────────────┘                     │
                      │                                          │
                      │  [1] /odom (센서 퓨전된 오도메트리 토픽)      │
                      │  [2] odom -> base_link (TF 방송)         │
                      │                                          │
                      ├──────────────────────────────────────────┘
                      │
                      ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 2단계: SLAM 노드 (slam_toolbox)                                              │
│  - /scan 과 /odom 을 받아 실시간 지도 작성 및 전역 오차 보정                   │
└─────────────────────┬───────────────────────────────────────────────────────┘
                      │
                      │  [1] /map (그리드 지도 토픽)
                      │  [2] map -> odom (전역 위치 보정 TF 방송)
                      │
                      ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 3단계: Nav2 (자율주행 및 제어 레이어)                                          │
│  - TF Tree (map -> odom -> base_link)를 참조하여 현재 위치 파악                │
│  - /map 과 /scan 으로 경로 생성 및 장애물 회피                                 │
└─────────────────────┬───────────────────────────────────────────────────────┘
                      │
                      │ /cmd_vel (로봇 속도/방향 제어 명령 토픽)
                      ▼
            ┌──────────────────┐
            │ 모터 컨트롤러 노드 │
            └──────────────────┘
```



# 2. 레이어별 핵심 역할 및 토픽/TF 데이터 흐름 정리
- ① EKF 노드 (센서 퓨전) 확장 칼만 필터(Extended Kalman Filter)
   역할: 빠르게 튀는 센서 값(바퀴 미끄러짐, IMU 노이즈)을 수학적으로 융합해서 미시적(단기적)으로 부드러운 위치 추정을 수행함.
- 입력 토픽: /wheel_odom, /imu/data
- 출력 토픽: /odom (Fused Odometry)
- 출력 TF: odom -> base_link (로봇이 방금 얼마나 움직였는가?)

- ② SLAM 노드 (지도 작성 & 위치 보정) SLAM(Simultaneous Localization and Mapping, 동시적 위치 추정 및 지도 작성)은
- 역할: EKF가 준 위치를 참고하며 라이다로 지도를 작성함. 시간이 지나며 EKF 오도메트리에 오차가 쌓이면, 라이다 스캔 매칭을 통해 거시적(전역) 오차를 보정함.
- 입력 토픽: /scan, /odom (또는 odom -> base_link TF)
- 출력 토픽: /map (OccupancyGrid 그리드 지도)
- 출력 TF: map -> odom (지도의 (0,0) 기준 odom 프레임이 얼마나 틀어졌는가?)

- ③ TF Tree (좌표계 변환 나무) 완성 구조
- Nav2 같은 자율주행 알고리즘이 "지도 기준 로봇의 현재 위치"를 계산할 때 보는 최종 좌표계 사슬이야.



```text
[map] ──(SLAM이 보정한 TF)──> [odom] ──(EKF가 연산한 TF)──> [base_link]
```


- Nav2의 위치 계산: $\text{map} \rightarrow \text{base\_link}$ 를 조회하면, 지도를 처음 켰을 때 기준 로봇의 정확한 $X, Y, \text{Yaw}$ 위치가 나옴!

# 3. 핵심 구분 포인트 요약/odom 
- 토픽을 발행하는 주체: $\rightarrow$ EKF 노드 (SLAM은 /odom을 읽기만 함)map -> odom TF를 쏘는 주체: $\rightarrow$ SLAM 노드 (지도를 새로 그릴 때) 또는 AMCL 노드 (만들어진 지도로 자율주행할 때)odom -> base_link TF를 쏘는 주체: $\rightarrow$ EKF 노드 (바퀴/IMU로 로봇 자체의 이동을 계산할 때)
- 추가적으로 생각해 볼 수 있는 아이디어 & 반대 상황
- ① 반대 상황: "만약 라이다(LiDAR)가 고장나거나 비산먼지로 막히면?"SLAM / AMCL 장애: 라이다 /scan 토픽이 끊기면 map -> odom TF 업데이트가 멈춰서 지도가 갱신되지 않거나, 지도 위에서 로봇의 진짜 위치(전역 위치)를 놓치게 돼.하지만 EKF는 동작: 라이다가 꺼져도 EKF 기반의 odom -> base_link TF와 /odom 토픽은 바퀴와 IMU로 계속 동작하기 때문에, 로봇이 즉시 멈추지 않고 단거리 비상 대피(Dead Reckoning)를 수행할 수 있어!
- ② 실무 확장 아이디어: "3D SLAM이나 카메라(Visual SLAM)를 쓸 때는?"2D 라이다 대신 3D Lidar (Velodyne, Ouster 등)나 Depth 카메라(Intel RealSense 등)를 쓰더라도 구조는 똑같아!입력 토픽만 /scan (LaserScan) 대신 /point_cloud (PointCloud2)로 바뀌고, SLAM 패키지만 3D용(LIO-SAM, rtabmap_ros 등)으로 교체하면 위 아키텍처 그대로 연동된단다.




```text
[하드웨어/센서]             [드라이버 노드]              [알고리즘 노드]
==============            ===============             ================
(바퀴 엔코더) --------->  WheelDriverNode  ---(/wheel_odom)--->  EkfFusionNode
(IMU 센서)   --------->  ImuDriverNode    ---(/imu/data)----->       │
                                                                     ▼
                                                                 (/odom)
                                                                     │
(2D 라이다)  --------->  LidarDriverNode  ---(/scan)--------->   SlamNode
                                                                     │
                                                                  (/map)
                                                                     │
                                                                     ▼
(실제 모터)  <--------- MotorControllerNode <---(/cmd_vel)--- SimpleNavigator
```















# urdf파일은 그럼 언제 넣는거야?
**URDF(Unified Robot Description Format)** 파일은 로봇 시스템이 작동하는 **모든 순간(시작부터 끝까지)** 백그라운드에 항상 띄워두어야 하는 로봇의 청사진(뼈대 지도)이야!
- 간단히 말해, 우리가 만든 Node들이 아무리 센서 값을 쏘고 알고리즘을 돌려도, **"로봇의 바퀴, 라이다, IMU가 실제로 서로 어디에 어떤 모양으로 붙어 있는지"** 정해주지 않으면 ROS 2는 아무것도 계산할 수 없어.
---

## 1. URDF는 실행 주기 중 '언제' 들어갈까?

- 시스템 관점에서는 **로봇을 드라이버/알고리즘 노드들과 함께 구동(Bringup)시키는 가장 첫 순간**에 띄워.
- Launch 파일로 로봇을 켤 때 다음과 같이 **두 개의 필수 노드**를 통해 URDF가 시스템 전체에 등록돼:

```
[URDF 파일 (.urdf / .xacro)]
           │
           ▼
1. robot_state_publisher 노드  ───>  /robot_description 토픽 발행 (로봇의 메쉬/형상 정보)
2. joint_state_publisher 노드  ───>  /joint_states 토픽 발행 (관절의 움직임 정보)

```

- 이 노드들이 켜지면, 우리가 아까 만들었던 드라이버 및 알고리즘 노드들이 URDF 정보를 바탕으로 각자 자기 할 일을 시작하게 되는 거야.

---

## 2. 우리가 만든 각 노드들은 URDF를 어떻게 활용할까?

URDF가 등록되어 있으면, 아래처럼 모든 알고리즘 및 시각화 노드가 이 정보를 실시간으로 가져다 쓰게 돼.

### ① LidarDriver & SLAM 노드

* **문제:** 라이다 드라이버가 점 구름 데이터(`/scan`)를 쏠 때, "이 라이다가 로봇 중심에서 앞(x)+20cm, 위(z)+15cm 위치에 달려있다"는 사실을 스캔 데이터 자체는 알지 못해.
* **URDF의 역할:** URDF에 `<joint name="laser_joint">`로 위치를 적어두면, ROS 2의 TF 시스템이 **`base_link -> laser_frame` 좌표 변환**을 자동으로 계산해 줘.
* **결과:** SLAM 노드가 라이다 스캔 데이터를 읽을 때, 로봇 중심 위치에 맞게 라이다 좌표를 자동으로 보정해서 지도를 그려.

### ② EKF (Sensor Fusion) 노드

* **문제:** IMU가 회전 속도를 측정할 때, IMU 칩이 로봇 회전 중심에 있는지, 아니면 한쪽 구석에 치우쳐서 달려 있는지에 따라 가속도/각속도 오차가 생겨.
* **URDF의 역할:** `base_link -> imu_link` 변환 값을 제공해서 EKF가 위치 오차를 감안해 칼만 필터를 계산할 수 있게 해줘.

### ③ Nav2 (충돌 회피 및 제어 노드)

* **문제:** 로봇이 장애물을 비껴갈 때, "로봇의 실제 가로/세로 크기(Footprint)"를 알아야 모서리가 벽에 걸리지 않고 통과할 수 있어.
* **URDF의 역할:** URDF 안의 `<collision>` 태그(로봇의 실제 물리적 충돌 크기)를 읽어와서 충돌 회피 영역을 계산해.

### ④ RViz2 (3D 시각화)

* **URDF의 역할:** URDF 안의 `<visual>` 태그(3D 메쉬 파일 등)를 읽어서, 모니터 화면에 실제 로봇 모양을 3D로 예쁘게 띄워줘.

---

## 3. URDF 파일 핵심 구조 한눈에 보기

URDF는 로봇의 부품인 `link`와 부품끼리의 연결 부위인 `joint`로 이루어진 XML 파일이야.

```xml
<?xml version="1.0"?>
<robot name="my_robot">

  <!-- 1. 로봇의 중심점 (기준 좌표계) -->
  <link name="base_link"/>

  <!-- 2. 라이다 링크 (물리 센서) -->
  <link name="laser_frame">
    <visual>
      <geometry>
        <cylinder radius="0.05" length="0.04"/> <!-- 3D 모양: 원통 -->
      </geometry>
    </visual>
  </link>

  <!-- 3. base_link와 laser_frame을 연결하는 관절 (물리적 위치 지정) -->
  <joint name="laser_joint" type="fixed">
    <parent link="base_link"/>
    <child link="laser_frame"/>
    <!-- 로봇 중심(base_link)에서 앞으로 20cm, 위로 15cm 위치에 센서가 있다고 지정 -->
    <origin xyz="0.2 0.0 0.15" rpy="0 0 0"/> 
  </joint>

</robot>

```

# 그럼 Bringup 할때 urdf 파일을 그러면 같이 넣어줘야되는거야?

```text

응, 맞아! 정답이야! 🎯

로봇을 켤 때 실행하는 Bringup 패키지(Launch 파일)에 URDF 파일(또는 Xacro 파일)을 읽어오는 로직을 무조건 포함해서 같이 띄워줘야 해.

왜 Bringup할 때 같이 넣어야 할까?
Bringup은 로봇의 "전원 버튼"이자 "출격 명령" 같은 거야.
하드웨어 드라이버(바퀴, IMU, 라이다)가 돌기 시작함과 동시에, robot_state_publisher라는 ROS 2 기본 노드가 URDF를 해석해서 다음과 같은 일들을 즉시 시작해야 하거든.

센서 좌표계(TF) 자동 생성:

라이다 드라이버가 쏜 스캔 데이터가 로봇 중심 기준 어디서 나온 건지(base_link -> laser_frame) 정적 TF(Static TF)를 지속적으로 방송해 줘.

로봇 3D 형상 파싱:

RViz 같은 모니터링 프로그램이나 Nav2, SLAM 알고리즘이 로봇의 크기, 충돌 외형(Footprint), 센서 위치를 곧바로 인식할 수 있게 해줘.

실제로 Bringup Launch 파일에는 어떻게 들어갈까?
실무에서 작성하는 ROS 2 Python Launch 파일 예시야.
보통 URDF/Xacro 파일의 위치를 찾아서 읽은 뒤, robot_state_publisher 노드에 파라미터로 넘겨주는 방식으로 작성해!

```

```python

import os
from ament_index_python.packages import get_package_share_directory
from launch import LaunchDescription
from launch_ros.actions import Node
import xacro

def generate_launch_description():
    # 1. URDF (또는 Xacro) 파일 경로 가져오기
    pkg_path = get_package_share_directory('my_robot_description')
    xacro_file = os.path.join(pkg_path, 'ros2_ws/my_robot_description/urdf', 'ros2_ws/my_robot_description/urdf/my_robot.urdf.xacro')

    # 2. Xacro 파일을 텍스트(XML)로 변환
    doc = xacro.parse(open(xacro_file))
    xacro.process_doc(doc)
    robot_description_config = doc.toxml()

    # 3. robot_state_publisher 노드 설정 (URDF 제공용)
    node_robot_state_publisher = Node(
        package='robot_state_publisher',
        executable='robot_state_publisher',
        output='screen',
        parameters=[{'robot_description': robot_description_config}]
    )

    # 4. 우리가 만든 센서/하드웨어 드라이버 노드들
    node_wheel_driver = Node(package='my_robot_driver', executable='wheel_driver_node')
    node_imu_driver = Node(package='my_robot_driver', executable='imu_driver_node')
    node_lidar_driver = Node(package='my_robot_driver', executable='lidar_driver_node')

    # LaunchDescription으로 모든 노드를 한 번에 실행!
    return LaunchDescription([
        node_robot_state_publisher,  # <-- URDF 파일 전달 담당!
        node_wheel_driver,
        node_imu_driver,
        node_lidar_driver,
    ])
```

# 정리: 역할 분담 구조 (분업)결국 ROS 2 로봇 시스템은 아래처럼 완벽하게 분업이 이루어져 있어!
|구분|담당 노드|사용하는 센서|주요 역할|
|---|---|---|---|
빠른 위치/속도 추정 (하위 레이어)|robot_localization (EKF)|휠 엔코더, IMU1|초에 50~100번씩 로봇의 실시간 **속도/이동량(Odom)**을 부드럽게 추정|
|주변 지도 매칭 및 장애물 회피 (상위 레이어)|Nav2 / SLAM (AMCL 등)|2D LiDAR (/scan)|EKF가 준 오도메트리를 바탕으로 지도 상에서 **주변 벽과 대조(Scan Match)**하여 누적 오차를 싹 보정함|
